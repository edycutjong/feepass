The story of FeePass

Paid in PUSD, a new user presses send.

The fee is due in BCH, and they hold none they can spend.

✕

Fee due in BCHno spendable BCH

↓

Lane pays it0.01 PUSD back

A new user is paid in PUSD, a dollar CashToken. Every Bitcoin Cash transaction needs a fee in BCH, and they hold none they can spend; getting BCH first means an exchange detour, an extra step before a new user can move any dollars. So we built the lane that pays the fee and let the user pay it back in the dollars they hold. The pain is protocol-level: we do not claim a named wallet shows a specific error; the ✕ is the state, not a screenshot.

Benefits of FeePass

  • No BCH detour
    • send the dollars you hold
  • Pay the fee in dollars
    • 0.01 PUSD per send
  • Busy lanes retry
    • random lane, same coin
  • Bounded loss per send
    • 2,000 sats max
  • Any wallet can run lanes
    • same MIT covenant
Each benefit maps to a covenant rule or a tested flow: R5 equality (exactly 0.01 PUSD to the pool); your wallet signs only its own coin; on a lane collision FeePass picks another random lane and asks for one more signature on the same coin (at most 2 re-signs, then "Pool busy: try again"), so two versions of one payment can never both confirm (test/flow.test.ts); R4 caps each send at 2,000 sats, but the covenant bounds each send, not the pool: many sends can still use lanes up. A wallet can run its own lanes with the same MIT covenant and its own fee; not yet tried with any wallet team.

function sponsorPaid() {
    // R1 fixed shape
    require(tx.inputs.length == 2);
    require(tx.outputs.length == 3);
    // R4 hard per-send cap
    require(tx.outputs[2].value >=
            tx.inputs[1].value - maxSubsidy);
    // R5 exactly feeTokens PUSD to the pool
    require(tx.outputs[2].tokenAmount ==
            tx.inputs[1].tokenAmount + feeTokens);
}
